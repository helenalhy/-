---
name: 訪客體驗與進度同步
description: App 的可選 Google 登入、本機訪客進度與雲端帳戶進度衝突處理原則。
---

使用者希望先以訪客身分體驗 App，再自行選擇是否用 Google 登入保存進度；登入後，App 重新開啟時應在工作階段仍有效的情況下保持登入。訪客資料先留在本機；登入時保留本機進度。若本機和帳戶各自已有不同進度，先讓使用者選擇保留哪一份，不能靜默覆蓋。

**Why:** 訪客模式和免重複登入是明確的產品要求；無提示覆蓋可能遺失目標、金幣或商場配置，而每次重開都登入會增加使用阻力。

**How to apply:** 保持未登入時可完整使用；新增帳戶資料時上傳本機進度，已有帳戶資料時先檢查本機是否有進度，只有兩邊都不同且有實際資料時才要求使用者確認。保留 Clerk 的持久 token cache；不要加沒有連到真實 session 行為的「記住我」勾選框。

使用者同意 App 個人檔案包含暱稱和預設插畫頭像；可選一般圖示或 14 隻毛茸茸狗狗店員圖片。訪客資料只存本機，登入後隨帳戶進度同步。這是 App 內的個人檔案，不修改 Google／Clerk 帳戶名稱或照片。

**Why:** 使用者明確選擇登入後跨裝置同步，並要求可選狗狗店員／卡通動物圖片；自訂圖片上傳並非目前已確認的範圍。

**How to apply:** 將暱稱與所有預設頭像 ID 納入同一帳戶快照；本機與雲端資料不同時沿用既有選擇流程，不可靜默覆蓋。

想減少的習慣、觸發情況和補充筆記屬於較私人的內容，預設只存在裝置本機，不納入一般目標進度同步。

**Why:** 使用者同意加入觸發記錄，但沒有要求把這類敏感自我觀察同步到帳戶或伺服器；預設本機保存可減少不必要的資料分享。

**How to apply:** 維持本機保存與明確提示；若日後要跨裝置同步，先提供清楚的自選同意，不能默默加入現有進度同步。

網頁版登入同步必須使用目前頁面的同源 API；原生 App 才使用建置時指定的完整 API 網址與 bearer token。

**Why:** 同一發布版可經不同別名或自訂網址開啟。將瀏覽器 API 固定指向建置網址，會令另一網址上的登入 cookie 無法隨請求傳送，產生「已登入但同步 401」的情況。

**How to apply:** 檢查同步授權問題時，先比對實際頁面 origin 與 API 請求 origin；不要靠網頁新增 bearer token 或修改 DNS 來掩蓋跨站請求問題。
